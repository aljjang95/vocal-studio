# Public booking boundary

The public Cloudflare Worker binds only to `BookingIntake`, a named service entrypoint in `worker/entry.mjs`. Default HTTP requests retain the existing Access, origin and protocol checks. No public booking list, Studio export, arbitrary commit or notification control is available.

`create({submissionId,clientKey,booking})` returns `{status,body,retryAfter}`. The UUID-v4 submission ID is stable across uncertain retries. `clientKey` is the public ingress SHA256 of Cloudflare's client IP. Booking fields are limited to name, phone, gender (`male`/`female`), ageGroup, goal, experience, preferredDay and memo. The caller cannot set a visit date/time, status, identity or canonical revision.

One SQLite transaction appends the inquiry, increments the canonical revision, stores a minimal receipt, increments rate counters and stores a notification outbox item. Existing record fields and all other collections remain unchanged. Same-phone requests create a marked inquiry for owner review without altering an existing customer. Preferred time bands never create appointments. The owner can schedule an exact visit through the existing authenticated inquiry workflow.

Receipt replay bypasses rate charging and returns the original receipt, including after runtime restart. Changed payloads using the same ID return 409. Limits are five new receipts per IP/10-minute window, three per phone/Korea calendar day, and 100 per day globally. Limit hashes expire at the end of each window; request bodies and IP addresses are not logged. Receipt IDs remain to prevent old uncertain retries from recreating deleted inquiries.

An alarm is durably installed before the outbox transaction. Notifications use an existing Telegram destination only when `BOOKING_NOTIFICATIONS_ENABLED=true` and Worker secrets `BOOKING_TELEGRAM_TOKEN`/`BOOKING_TELEGRAM_CHAT_ID` exist. Missing configuration retains pending items and retries hourly. Other failures retry with capped exponential backoff. Short serialized sections claim at most two messages with a durable 60-second lease, then release the canonical gate during external I/O. The lease recovery alarm is set before each claim. Results update only a matching lease token; every settlement reschedules the earliest pending item or outstanding lease. A crash after an acknowledgement leaves a recoverable lease. A booking acknowledgement proves durable intake, not successful notification or a confirmed appointment. Telegram has no idempotency key: delivery after an ambiguous response can repeat the same clearly labelled receipt ID. Successful delivery clears the outbox body and retains the message ID.

The authenticated protocol route `GET /api/intake/notifications` returns up to 100 status receipts without contact details. It cannot send an arbitrary message. Applicant text uses no Telegram markup mode. Network failures and upstream descriptions are not exposed in public errors.

Schema is additive in the existing `StudioState` SQLite namespace; no new DO class or destructive migration is required. Rollback to the preceding Worker preserves the tables but suspends new intake and outbox processing. Restore the intake Worker to resume. Preserve pending outbox items when rolling back.

Local validation: `node --test scripts/intake.test.mjs`; build a Wrangler dry-run bundle into `work/intake-bundle` then `node scripts/intake-workerd.mjs`. The latter uses two real local Workers, named RPC, SQLite persistence/restart and an actual DO alarm with a synthetic Telegram service. No live Telegram delivery is claimed from this test.
